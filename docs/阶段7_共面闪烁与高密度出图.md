# 阶段 7 · 共面闪烁与高像素密度出图

两条主线：**（一）墙面与内外附着构件的共面争夺（转视角条纹闪烁）**、**（二）320 档高像素密度的出图卡顿**。
全部改动都在渲染器 / 构件库内部，配方与预设结构未动；`node cli/preset-audit.js` 64 套 error 0 warn 0。

---

## 一、共面闪烁

### 判据

两条渲染路径（CPU 软件光栅、GPU 硬件光栅）都是 **z-buffer 逐像素「严格大于才落笔」**，且都 **关背面剔除、法线朝相机翻正**。
所以两个三角面只要 **法线平行 + 平面常数 d 相同 + 投影后真实重叠**，胜者就取决于浮点噪声与遍历顺序——转视角时条纹、跳格、忽隐忽现都由此而来。
这不是"深度精度不够"，改 near/far 或加 bias 都治不了，只能让同面不再同面。

检测工具：`node cli/coplanar.js <preset> [ppm] [tagRegex] [minArea]`（网格加速，1/1000 容差，输出按构件标签对排序的共面面积表）。面积合计 = 0 即彻底没有可见的共面争夺。

### 四类根因与改法

1. **六面盒栅格化（墙体）** —— `wallWithHoles()` 原来把带洞口的墙切成栅格，每格出一个**完整六面盒**（12 个面）。格与格之间的切缝两侧各留一张面，严格同面且真实重叠。清式整殿仅"墙体×墙体"就有 26.6 m²。
   → 改成**只出壳**：每格只出内外两张墙面（2 个面），侧壁只在"真边界"（墙端、洞口边、墙顶墙脚）出现，栅格内部切缝不出面。同时面数从 12/格降到 2/格。
2. **叠罗汉式构件上下同面** —— 压顶压墙顶、脊压压顶、普拍枋压额枋、柱头枋压栱眼壁、窗楣线压窗楣、窗楣压窗框、勒脚压墙底：上层底面与下层顶面是同一张水平面。
   → 统一改成**上层压进下层 4～8 mm**（`lap`）。视觉上是正常搭接，几何上同面消失。
3. **相邻盒体面对面** —— 相邻门扇的边梃/抹头、窗框内缘与洞口侧壁、裙板线与裙板、松檩与松檩：两个盒子的立面在同一平面且真实重叠。
   → 改成**交界处互相咬进 2 mm**（门扇左右各外扩、窗框内缘咬进洞口、裙板/线条压进板面）。
4. **同一张面正反两套三角** —— `Mesh.prism()` 的顶底扇面、屋面三角山花：当年为躲背面剔除把正面和反面各铺一遍，两片严格同面。塔的"平座铺板"因此叠出 91 m²。
   → **只留一片**。渲染器不做背面剔除、法线还会朝相机翻正，反的那套纯属白画。

### 结果（ppm 320，全模型）

| 预设 | 改前（对 / m²） | 改后（对 / m²） |
|---|---|---|
| qing（清式七檩歇山） | 963 / **79.52** | 77 / **4.20** |
| siheyuan（五进四合院） | 1092 / **124.96** | 155 / **19.57** |
| ta（楼阁式塔） | 238 / **223.40** | 0 / **0.00** |
| tingtang（厅堂） | 650 / **70.45** | 79 / **8.14** |
| luntai（露台） | 20 / 1.05 | 20 / 1.05 |

五套合计 **499.4 m² → 33.0 m²（−93.4%）**；qing 的"墙体×墙体 26.6 m²""墙脚石 11.3 m²""斗拱华栱×昂 6.2 m²""栱眼壁带 5.4 m²"全部清零。

面数同步下降（顺带减负）：qing 204812 → 204208；siheyuan 162168 → 161022；ta 128118 → 127402（塔的重复盖板直接省掉 716 个三角面）。

### 遗留

合计 33 m² 里，qing 剩下的大头都是**家具与石雕内部件**，不在受光立面：
香案×香案面 0.94、栏杆望柱×望柱 0.72、石狮座×身 0.48、屋面瓦条×瓦条（正脊被重复生成两次，属同一处 bug 的另一面）等。
这类属于"同一部件被生成两遍"的重复件，改法与前四类相同（去重或错位），本轮先不动——它们不影响任何可见轮廓。

## 二、高像素密度出图卡顿

### 定位：卡的不是预览，是"全精度出图"

预览帧被 `PREVIEW_MAX_PIXELS = 2.6M` 封顶，**高 ppm 并不增加预览像素**，只是把几何细节抬到 det3。真正的天量在导出：

| 预设 | ppm | 全精度画幅 | 像素 |
|---|---|---|---|
| qing | 320 | 10778×8796 | 94.8M |
| siheyuan | 320 | 10345×7303 | 75.6M |
| qing | 160 | 5397×4406 | 23.8M |

单张 PNG 一次光栅化 95M 像素；八向精灵表 8 次、ZIP 4 次（这两处本来就已经逐帧 `await nextFrame()` 让出主线程，不会假死，但总时长感人）。

### 瓶颈实测（headless Chrome + 本机 AMD Radeon，`GF.renderGPU` 端点）

GPU 路径原来的尾段是四趟全图扫描 + 三张全图数组：

1. `readPixels` 颜色 95M×4B，再 **逐像素** 拷进 `rgba`（95M 次循环）；
2. `readPixels` 信息缓冲，再逐像素解包出 `matId`(Uint16) / `depth`(Float32) / `shadeIdx`(Uint8)；
3. 描边：逐像素建 `[[x-1,y],[x+1,y],…]` 数组做 4 邻域；
4. 落墨：再扫一遍全图写色。

320 档峰值内存约 2.5 GB（`bufC`+`bufI`+`rgba`+三张表），光栅之外的这四趟就是 3.4–4.4s 的大部分。

### 改法

- **行翻转**：`readPixels` 原点在左下，改成**原地成对交换**，省掉一整张 95M×4B 的副本；
- **不再解包**：材质号（含地面位）与 16bit 深度就在信息缓冲里，邻域直接按字节读；"深度差 > 0.35 m"这个 CPU 判据换算成 **16bit 整数阈值** `th16 = 0.35/zSpan*65535` 做整数比较；
- **勾线单趟**：判边与落墨合并，像素风直接就地写 `bufC`（邻域只看 alpha / 材质号 / 深度，三样都不受改色影响）；
- **按需分配**：`shadeIdx` 只有画风（水墨/枯笔/双色）才建；`edgeMask`/`innerMask` 只有画风才建，像素风一张不留；
- **转折压暗查表**：`DIM62`/`DIM66` 两张 256 项表用 `Uint8ClampedArray` 生成，取整（含 x.5 的银行家舍入）与旧实现逐位一致；
- `composeSheet` 拼精灵表改成**逐行整拷**（原来逐像素赋四个通道）；
- CPU 光栅同步瘦身：世界坐标按 x 逐像素递推、肌理轴向判定提到三角面级、`matId` 降成 1 字节、遮罩/`shadeIdx` 按需分配、勾线由"两张遮罩 + 两趟扫描"合成一趟。

### 结果

| 场景 | 改前 | 改后 |
|---|---|---|
| qing 320 全精度 GPU（94.8M px） | 3.4–4.4s | **0.93–1.27s** |
| siheyuan 320 全精度 GPU（75.6M px） | — | **0.72s** |
| qing 160 全精度 GPU（23.8M px） | 0.96s | **0.34–0.39s** |
| qing 64 全精度 GPU（3.8M px） | 0.26s | **0.09–0.13s** |
| qing 320 预览帧（2.6M px） | ~0.25–0.4s 量级 | **0.13s** |
| qing 320 全精度 CPU | 11.87s | 10.91s（−8%） |
| qing 160 全精度 CPU | 3.27s | 2.99s |

GPU 320 档从 3.5s 级降到 1s 级（约 3×）；64 档一把从 0.26s 降到 0.10s，滑块连续调时的拖影基本消失。

### 像素一致性（必须为 0，已验证）

拿 `git show HEAD:js/gf-render.js` 当旧内核，在同一个页面里先存旧 `GF.renderGPU`、再加载新内核，**同一 mesh、同一参数**跑两遍逐像素比对：

```
qing  ppm64   outline=1           diff pixels=0  maxd=0
qing  ppm160  outline=1           diff pixels=0  maxd=0
qing  ppm160  outline=0           diff pixels=0  maxd=0
qing  ppm320  outline=1           diff pixels=0  maxd=0
qing  ppm64   style=ink amt=.8    diff pixels=0  maxd=0      （含勾线）
qing  ppm64   style=ink amt=.8 outline=0  diff pixels=0  maxd=0
qing  ppm96   style=watercolor    diff pixels=0  maxd=0
siheyuan ppm64                    diff pixels=0  maxd=0
```

CPU 路径同样逐字节一致（改造前后全图 FNV 双哈希相同：`c457dacd:3dcd3e08`(ppm64)、`f2d347c0:c0cb4b70`(ppm160)）。
中途发现并修掉的两处"看似等价其实不等价"：`Uint8Array` 直接赋值是**截断**而 `Uint8ClampedArray` 是**四舍五入**（差 1 LSB，22984 像素），以及不勾线时遮罩应保持全零而不是不建。

## 三、验证命令

```bash
node cli/preset-audit.js              # 64 套预设结构审计
node cli/coplanar.js qing 320         # 共面重叠（面积合计应接近 0）
node cli/coplanar.js siheyuan 320
node cli/render.js --preset qing --ppm 160 --out out/qing.png
```

本轮出图（`out/阶段7_共面/`）：`qing_22.png`、`qing_40.png`、`qing_160.png`、`siheyuan_40.png`、`ta_30.png`、`tingtang_40.png`——用于确认壳化墙体、窗框咬边、山花去重、塔身盖板去重之后**没有任何缺面/透空/翻面**。

## 四、取舍与未做

- **共面残留 ~33 m²** 集中在家具/石雕内部件与"正脊被生成两次"这类重复件上，不影响可见轮廓，未处理。
- **CPU 光栅只快了 8%**：真正的热点是逐像素的色阶 / 肌理数学（约占 preview 帧 32%），要再快得改算法（预烘焙肌理到纹理图集）而不是抠循环，本轮未动。
- **没有做分带/分块渲染**：320 档 95M 像素目前已经能在显卡单张 FBO 里一次画完（本机 `MAX_TEXTURE_SIZE=16384`），分带只在纹理上限更小的机器上才有意义；超限仍是老规矩——回落 CPU。
- **预览像素预算（2.6M / dpr 1.25）未改**：这属于画质取舍，需要用户拍板。
